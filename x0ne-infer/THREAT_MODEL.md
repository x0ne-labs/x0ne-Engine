# x0ne Engine — threat model (living document, started 2026-08-20)

Scope: the inference server (`x0ne-infer`) running inside a confidential VM
(Intel TDX) with NVIDIA GPU(s) in confidential-computing mode, serving a
model whose weights are the client's asset, on infrastructure owned by an
untrusted operator (a cloud, later any GPU provider). The chat model runs on
x0ne Core, on the GPU (`x0ne-core/`, `x0ne-infer/src/core_backend.rs`).

## Adversaries considered

| Fake/replayed attestation | replays an old quote or token | nonce echoed in TDX report_data AND NRAS eat_nonce, both COMPARED on return; same nonce ties the two halves | done. GPU half: nonce checked, and since 2026-09-18 each token's `ueid` too (next row) |
| GPU relay (TEE.fail: NVIDIA quotes "are not bound to the identity of a specific CVM") | forwards our GPU challenge to a genuine CC GPU elsewhere, serves from whatever is in the machine | each per-GPU NRAS token is verified (signature, nonce, `measres`, NVIDIA's published policy claims; since 2026-10-18 its three certificate chains `valid` with OCSP `good` and no opaque-data mismatch, as NVAT's default policy, plus `secboot` true and `dbgstat` disabled, a hardening NVAT's default does not read, `nras::gpu_policy`) and its `ueid` must equal the serial of the attestation certificate read from the LOCAL GPU (`nras::verify_nras_attestation`); since 2026-10-23 the overall token's `submods` must name each per-GPU token by its SHA-256 and nothing else, so the overall verdict and the per-GPU tokens come from one NRAS answer (`nras::check_submods`; the shape and the digest are those of the production token of 2026-10-17; NVAT checks the digests and their number, not the label, which is read more strictly here: `SHA-256` or `SHA256`); since 2026-10-24 a local certificate serial named twice is refused, so one GPU's token cannot stand for two | done 2026-09-18 on fixtures, mutation-checked; the `ueid` derivation comes from NVIDIA's nvtrust SDK and has met production tokens in cloud mode on 2026-10-14 (`RUN_2026-10-14_beta2.md`), 2026-10-17 and 2026-10-18, where it matched each time — a wrong derivation refuses, it does not admit. | Shard set manipulation | publisher, mirror or operator reorders, swaps, adds or drops shards, or edits the index | weight files taken from the catalog entry, never a directory listing, each against its sha256; the index and the shard headers must agree exactly; a tensor in two shards, a shard the index does not name or one it names and is missing, a key twice among a header's tensors, in one tensor's fields or in `weight_map`: refused (72 in cloud mode); keys inside a header's `__metadata__` and the index's `metadata` are not checked, no tensor is read through them (`shards.rs`, test `the_duplicate_key_check_covers_tensors_their_fields_and_weight_map`); each tensor read from the shard the index names (`shards::Routing`), never "last file wins" | done 2026-10-17, tests on synthetic shards and qwen3:1.7b (`shards.rs`, `registry/tests.rs`, `tests/real_model.rs`); never run on a TD |
| Secrets in logs/dumps/swap | plaintext escapes sideways | `Zeroizing` key material, no `Debug` on secrets, receipts carry digests only | partial: the 32-byte key and the hex string it is parsed from (`HeldKeyBroker`, `keys.rs`) are zeroized on drop; the environment variable is removed and its exec-time value overwritten at start-up (`take_env_key`); server lifecycle (drain/zeroize) not built. The files that hold the answer's text (`stream.rs`, `sse.rs`, `local_api.rs`) carry no log macro, `tracing`, standard output macro or raw `io::stdout()`/`io::stderr()` handle, and say so in their header; `tests/no_log_on_answer_paths.rs` holds each file to its header and those three paths to the claim (Trail of Bits found inference data logged by client code in Meta's Private Processing, 2025, finding 5) |
| Prompt-hash dictionary attack | receipt hash of low-entropy prompt inverted | receipts commit with a per-request salt (keyed commitment), never bare SHA-256; the opening is returned to the caller only | done (`receipt.rs`, `verify_commitment`) |
| Another tenant of the same engine | reads across requests through a shared KV or prefix cache, or through cross-client batching | none of those exist across requests here: the KV cache of a request without a conversation is dropped on every exit path of `generate_turn`, zeroed first by x0ne Core with the request's other bytes (activations, logits, host buffers; a failed zeroing poisons the engine, and the next request zeroes again before it runs: `x0ne-core/runtime/src/engine.rs`), there is no prefix cache at all, and the engine runs one request at a time behind a `Mutex`. Since 2026-10-30 a request may ask to keep its own conversation's keys and values for its next turn (`x0ne.conversation`): one conversation at a time, found by a TD-drawn single-use handle bound to its route, never by content, zeroed before any other request runs and after 300 s without a turn (`docs/session-kv-cache.md`). Each is asserted in every receipt, under the signature | done. The receipt values are constants of each path (`Isolation::NONE_OF_IT`; on a turn of a conversation the KV-cache flag `true` and a signed `context` block, which the relay and the SDK hold to the request), not per-request measurements; two of the four claims are guarded by tests that read this crate's source (the cache settled after a call that captures every failure, no logging macro near prompt text), not dependencies |
| Operator selling the cheap product as the expensive one | serves CPU inference on a GPU-attested machine, or lets a GPU attestation failure degrade into a CPU-only service | the receipt names the processor that ran the arithmetic; a CPU-only verdict cannot describe a GPU; `--attest cpu` is refused in this version, and a GPU attestation failure exits non-zero | done |
| Supply chain (the binary itself lies) | attested measurement of a malicious build | reproducible builds + Sigstore provenance + published measurements | written, not exercised by this tree's tests: `.github/workflows/release.yml` builds the release binaries twice on two runners, refuses if they differ and attaches SLSA build provenance (Sigstore); `make repro-compare` compares the builds of two environments (one machine so far, image row above); no published measurement has release provenance yet (image row above); Tinfoil is the reference bar |
| Access-pattern leak of the prompt during tokenization | host observes the guest's memory accesses (controlled-channel page faults at 4 KiB, physical-alias cache probes at 64 B) and, since the hash and table layout are public, reads the tokenizer's secret-dependent hash-map lookups back to tokens (TDXRay, IEEE S&P 2026: 91.5% Llama 3.2, 94.2% Gemma 3 from one tokenization; Intel SA-01271, AMD SB-3044). De-tokenization is the output analogue (Spill the Beans, arXiv:2505.00817) | R&D: a data-oblivious tokenizer whose instructions and data addresses are a function of the piece's UTF-8 byte length only, token output equal to the stock tokenizer's on the test fixture (`oblivious_tok`, `docs/oblivious-tokenizer.md`). Exposure measured on a fixture (simulated trace); the fix measured on the release binary under valgrind lackey (`scripts/obtok-trace.sh`): identical instruction and data-address sequences within each byte length, where the previous merge stage differed | NOT in the serving path. Measured, not shipped: the leak is reproduced and a prompt reconstructed on a fixture; the oblivious tokenizer matches `tokenizers`' BPE token-for-token. Not covered: normalization and the regex pre-tokenizer, the byte length of each piece, the allocator (`tokenize` allocates; only `tokenize_into` with a reused buffer is claimed), cache state, another compiler build, the ids once returned; production overhead needs an oblivious map (Oblivious Labs) not the current linear scan |

## The attested channel — `x0ne-engine-proxy` ↔ `x0ne-infer --cloud-config`

The cloud path removes "Transport is
not attested" for one route only: the relay on the user's machine
terminates TLS 1.3 inside the TD, pins the TD's key through the quote and
verifies everything itself before the first byte of a question leaves.
Status of every row below: **simulated** — the real relay and the real
server code, synthetic quotes and tokens under test roots on the loopback
(`src/cloud_e2e_tests.rs`), one real Google endorsement (`tests/VENDORED.md`).
Two runs on real hardware since, each on one GCP TDX + H100 spot VM.
0.2.0-beta.2 on 2026-10-14 (`RUN_2026-10-14_beta2.md`): the relay's
verification passed with Intel PCS, Google's endorsement and NRAS fetched
live, a session quote replayed onto another connection and a foreign client
certificate were refused, and the TD did not resume a session when asked.
0.2.0-beta.5 on 2026-10-17, through `x0ne-engine cloud run`:
verdict VERIFIED, RTMR1 and RTMR2 matched a v1 reference taken unsigned
(that client predates the signature check), key released, receipts
verified (`docs/hardware-runs.md`). The rows keep their simulated
status: one VM and one client each time, a rate that did not reach the
quote limits.

## AMD SEV-SNP (the client's verdict, 2026-10-28)

`src/snp.rs` verifies an SEV-SNP attestation report. The relay runs it: a
session whose `--reference` is an SEV-SNP reference
(`x0ne-engine/snp-reference/v1`, `snp_reference.rs`, signed by the archive
key and shown in the pinned log by the same code as the TDX reference)
verifies the guest's document with `remote_verify::verify_snp_document` and
each connection with `SessionCheck::snp`. A session pins one TEE: an SEV-SNP
reference refuses a document or a session attestation carrying TDX
evidence, a TDX reference refuses one carrying SEV-SNP evidence (88), and
neither falls back to the other nor to an unverified verdict (tests). On
the guest side, x0ne-infer verifies its own report the same way before it
serves (`attest_v2::attest_snp`), with AMD's CRL the image leaves at
`/run/x0ne/snp-crl.der` (absent: exit 76). No SEV-SNP machine has run this
code, and none of the rows above has been measured on one.

What a verified SEV-SNP document proves, given the checks the code makes:

- **AMD signed it, through a pinned root.** A VCEK must chain to an ARK and
  ASK pinned by SPKI digest (Milan, Genoa, Turin), a VLEK to the ARK and the
  ASVK ("SEV-VLEK-<product>", pinned the same way, measured on KDS
  2026-10-28); RSASSA-PSS SHA-384, salt 48; every certificate in its window;
  the report's ECDSA P-384 signature under that key. The key's source (the
  guest's certificate table, a cache) is untrusted; its signature is the
  link. A chain to another root, an ASK of the same name under another ARK
  and a key presented as the other kind are refused (tests). A VLEK is
  accepted only for a cspId the reference lists; the default lists none.
- **Not revoked, as far as AMD publishes.** AMD's CRL for the product,
  fetched from KDS at each verdict, must be signed by the pinned ARK, be
  read inside its window and not list the ASK or ASVK of the chain; KDS's
  `Date` must be within 300 s of this machine's clock (87), and KDS
  unreachable refuses (76). AMD's Genoa CRL of 2026-10-27 lists one serial,
  not the pinned ASK (test on AMD's file).
- **That chip, at that TCB.** For a VCEK, `CHIP_ID` is its hwID; for both
  keys `REPORTED_TCB` is the key's SPL extensions and `CPUID` (report
  version 3 and later) names the same product line. A masked chip ID and a
  report requested by the host or at a VMPL other than 0 are refused.
- **Firmware at or above a written floor.** Reported, current, committed and
  launch TCB are each held, component by component (boot loader, TEE, SNP,
  microcode, and FMC on Turin), to the default compiled from AMD's bulletins
  (SNP firmware from AMD-SB-3020, microcode from AMD-SB-3027, and on Milan
  and Genoa the BadRAM alias check of AMD-SB-3015), raised by the
  reference's `tcb_minimum` and never lowered by it. Under the relay's
  `transparent` TCB policy, the default since 2026-10-28, a bulletin is
  imposed once a year has passed since its date (a constant of `snp.rs`)
  and only named before, with what the report misses of it, in the verdict
  and its `tcb` disclosure: a guest served under `transparent` may lack the
  fixes of a bulletin less than a year old. Under `strict`, every bulletin
  is imposed. On 2026-10-28 the two differ on AMD-SB-3027 only, named
  until 2027-01-15; where its own microcode floor is not in hand,
  AMD-SB-3020's is imposed for both.
- **No debugging, no migration agent.** DEBUG and a migration agent
  (allowed by policy, or named by `REPORT_ID_MA`) refuse, and no field of
  the reference can allow them. SMT refuses (`POLICY.SMT` or
  `PLATFORM_INFO.SMT_EN` set) unless the reference writes `allowed`, and the
  verdict then says a sibling thread may run host code. A `POLICY`,
  `KEY_INFO` or `PLATFORM_INFO` bit this verifier does not know, and a
  reserved byte set, refuse.
- **This image.** `MEASUREMENT` must be one of the reference's
  `launch.measurements_sha384` (65). `HOST_DATA` must be the reference's
  `launch.host_data` when it pins one; when it does not, the verdict says
  `HOST_DATA` was not judged.
- **This session, this connection.** In the document `REPORT_DATA` is the
  TDX binding (SHA-512 over context, nonce, session key, TLS key, config,
  88). Each connection's report must be the document's byte for byte but
  `REPORT_DATA`, under the same VCEK or VLEK, and bind `BindingV3` over that
  connection's TLS exporter (88).
- **The GPU, as with TDX.** With `--attest cpu+gpu`, NRAS tokens for the
  session's GPU nonce in the document, and on each connection for
  `session_gpu_nonce(exporter, the report's signed bytes 0x000-0x29F)`,
  naming the document's GPUs. CPU and GPU are bound by the guest's
  software, not by hardware, as on TDX.

What it does not prove, and why:

- **Where the launch digests come from.** The reference lists digests
  predicted outside this verifier from the firmware, kernel, initrd, command
  line, vCPU count and type; its signer vouches for those inputs and nothing
  in the client rebuilds them. `MEASUREMENT` covers what the host loaded
  before launch; what the guest loads afterwards is covered only through the
  code that digest names. There is no event log and no RTMR.
- **Milan.** Shen and Qin (preprint, 2026-05-13,
  <https://arxiv.org/abs/2605.12990>) describe forging Milan attestation
  reports. Milan is pinned but refused unless the reference lists it; a
  Milan verdict proves less than its chain suggests.
- **A single chip key's revocation.** AMD's CRL lists ASKs and ASVKs; a
  VCEK or VLEK has no CRL of its own. A compromised chip key is caught only
  by the TCB minimum, if at all. AMD has no live TCB service like Intel PCS:
  the minimum is what this build compiles in, raised by the reference, and
  a newer bulletin reaches a client with a new build or a new reference.
- **A VLEK names a provider, not a chip.** `CHIP_ID` is not checked under a
  VLEK; the verdict says so.
- **Physical memory.** TEE.fail (AMD-SB-3040, 2025-10-28, DDR5) and DDRop
  (AMD-SB-3048, DDR5 fault injection) interpose on the memory bus; AMD
  states that physical attacks are outside SEV-SNP's threat model and plans
  no mitigation. BadRAM, WireTap and Battering RAM are the DDR4 family. A
  verified report proves a machine AMD vouches for, not the absence of an
  interposer; a host operator has physical access by definition.
- **Ciphertext side channels.** Heracles and Relocate+Vote (AMD-SB-3021) read
  guest secrets through ciphertext the hypervisor can see. AMD's answer is
  ciphertext hiding from Turin on and a page-swap restriction in the guest
  policy; neither bit is judged here, nor single-socket, AES-256-XTS, RAPL
  or CXL.
- **v5 mitigation vectors** (`LAUNCH_MIT_VECTOR`, `CURRENT_MIT_VECTOR`) are
  in the report and in the verdict, not judged.
- **The model key and the caller-sealed path.** Sealed weights are released
  to TDX guests only: the relay refuses `--model-key` with an SEV-SNP
  reference (89) and a recipient check on an SEV-SNP session refuses (88).
  The SDK's `/v2/e2e` path verifies a TDX quote only.
- **Azure.** A report made by Microsoft's paravisor is not one the guest
  binds to the session; `--provider azure` stays refused, and a genuine
  Azure report through the client path is refused (test).
- **A host to run it on.** `x0ne-engine cloud` creates GCP TDX VMs only; the
  relay's config event for an SEV-SNP reference names no GCP image, and the
  GCP lifecycle refuses it.
  No tool to launch an SEV-SNP guest ships in this repository.

## Explicitly OUT of threat model (today)

- **Availability**: the operator can refuse to run, stop, throttle. CC
  protects confidentiality and integrity, not uptime. The GPU half of a
  verdict is a token from NVIDIA's NRAS service, fetched live at each session
  (`nras.rs`): with NRAS unreachable, a session, which attests a GPU
  (`--attest cpu+gpu`, the relay's only value since 2026-11-04), gets no
  verdict and does not start, and no other appraiser is read. Intel Trust Authority says the
  same of its own tokens: when NRAS "is unavailable, an error will occur"
  and it "won't return an attestation token" (concept page, updated
  2026-06-16,
  <https://docs.trustauthority.intel.com/main/articles/concept-gpu-attestation.html>).
- **CPU↔GPU hardware binding on Hopper**: the TDX quote and the GPU evidence
  are tied by our nonce and by collection from inside the CVM, not by a
  hardware cross-signature (Hopper has none). Since binding v4 the nonce of
  each connection's GPU evidence derives from that connection's TLS
  exporter and its quote: the strongest link software can make, and one that
  falls with the CPU TEE. A forged quote (TEE.fail) comes with a TLS session
  its forger terminates, so with its exporter, and any genuine GPU in CC
  mode answers any nonce. An adversary with root INSIDE the attested CVM is
  out of scope (the binding is session-level, not device-level). Revisit on
  Blackwell.
- **Side channels** (timing, power, controlled-channel on TDX): acknowledged,
  not addressed at this layer, except the sizes and timing of a stream's
  records on the network, padded (the table's row on them says what stays
  visible). The padding does not reach the computation: the host reads an
  answer's length from it (row "Host reading an answer's length from the
  computation").
- **Physical memory interposition**: TEE.fail (2025-10, DDR5, TDX and
  SEV-SNP up to date) reads guest memory through a bus interposer under
  1 000 $ and extracts attestation keys, which its authors say "can be used
  to compromise NVIDIA's GPU Confidential Computing"; WireTap and Battering
  RAM (2025-09/10, DDR4, SGX and SEV) are the same family. DDRop (ACM CCS
  2026, DDR5, under 200 $) forges attestation reports and forces a TD into
  debug mode on an up-to-date TDX platform. Intel's position is that
  physical access is required. Consequence for every row above: a verified
  quote proves a machine Intel and NVIDIA vouch for, not the absence of an
  interposer on it. The party with physical access to the host is the cloud
  operator, the adversary of the first row, and a quote forged this way
  cannot be told from a genuine one by the client. Sources and the other
  published attacks: "Known attacks as of 2026-10-22" below.
- **Transport**: the server speaks plain HTTP on the address it is given;
  nothing about the connection to it is attested, and nobody is
  authenticated. Only the `Host` is checked (localhost, 127.0.0.1, `[::1]`
  and `--allow-host` names, else 421), which stops a page whose name
  rebinds to the server, not a client that reaches the port. Its streams
  use the TD's padded body, so that behind a TLS terminator they would not
  show token sizes and timing either; in plain HTTP the text is readable.
- **The client's own machine** (where the KEK will live) being compromised.
- **Malicious model weights** (the model doing bad things when asked): that
  is the agent-side policy's domain (x0ne Harness), not the server's.
- **Model files mapped, not copied** (0.2.0-beta.6): the weights are read
  through a read-only `mmap` of the model store, and the served digest is
  computed over the same mappings. A process that can write those files
  after the check changes what is loaded without changing what was hashed,
  and a truncation ends the server (SIGBUS). In a TD the store is a tmpfs in
  the guest's memory: whoever can write it is inside the guest the quote
  measures. On a workstation it is the local user, as before
  (`docs/pull-run.md`, "What it does not do"). Mapped is not "never in host
  memory": in CC mode each host-to-GPU copy is encrypted and signed by the
  guest's driver into bounce buffers in memory shared with the host, then
  decrypted by the GPU (NVIDIA, 2023, "Confidential Compute on NVIDIA Hopper
  H100", WP-11459-001, pp. 11 and 27,
  <https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf>).
  The host sees the weights pass encrypted; their confidentiality on that
  path rests on that encryption.

## Promises this project does not make

None of the texts of this repository may make these promises. The test
`tests/public_claims.rs` reads every Markdown file, the unreleased part of
CHANGELOG.md, CITATION.cff, the package descriptions and the served pages,
and fails on the phrases listed for each rule below, a fixed list (the
same promise in other words is not caught), unless
`tests/public_claims/allowed.tsv` lists the occurrence with the reason it is
not the promise (a negation, the name of a test). This section is the only
text it does not read.

## Invariants (each is or must become a test)

1. No proof, no socket (`gate.rs` — done). Holds for `x0ne-infer`.
2. The key is read only after proof, and the decision is re-taken on the
   same evidence (`keys.rs` — done). In v0 the key is already in the process
   environment before the proof; the invariant is about when it is READ.
3. A structural verdict never serves (`gate.rs` test — done).
4. Composite = CPU AND GPU, same nonce (`verify.rs` — done). Since binding
   v4, every connection of the GPU product re-attests the GPU for a nonce
   derived from its TLS exporter and its session quote, and the relay
   refuses tokens for any other nonce or GPU (`binding.rs`,
   `remote_verify.rs`, `cloud_e2e_tests.rs` — done on fixtures).
5. Receipts never carry plaintext, and their signing key is bound into the
   attestation (report_data) — done (`binding.rs`, `receipt.rs`; on an early hardware run the
   session pubkey in `/attestation` verified the receipt).
6. `x0ne-infer` cannot be built into a server that skips attestation: no
   feature substitutes its evidence source, and the gate refuses a
   `Standard` environment before reading any verdict (`evidence.rs` test —
   done, 2026-08-21).
7. Sealed weights are unreadable without the key, and any flipped bit is a
   refusal, never a wrong plaintext (`seal.rs` tests — done). In cloud mode
   the owner's key opens only in the TD whose quote named the X25519 key it
   was wrapped to, for the one release nonce that TD issued
   (`model_key.rs`, `cloud_e2e_tests.rs` — done against the simulated TD).
8. The environment a proof publishes is the VERDICT's, never the collector's
   self-report (`verify.rs` test on the full composite path — done, 2026-08-20).
9. A verdict never satisfies a policy it cannot express: a CPU-only proof
   refuses `require_gpu_cc_on`, and any proof refuses a policy that does not
   accept its CPU technology, Intel TDX or (`cryptographic_snp`, 2026-10-22)
   AMD SEV-SNP (`verify.rs` — done, 2026-08-22; both
   fields were read by the STRUCTURAL verifier alone until then).
10. The server stops answering once the lease its key was released under has
    expired (`server.rs` — done, 2026-08-22; the claim predates the
    check by the whole life of the file). Since 2026-10-11 the lease runs on
    the monotonic clock as well as the wall clock, a wall clock moved back
    more than 60 s ends it, and it is re-checked when a computation starts,
    after the queue (`serving_lease.rs`). A host that pauses the guest stops
    its monotonic clock: the bound is 24 h of guest running time.
11. Every field of a receipt is under its signature, and the console compares
    all of them rather than a list somebody must remember to extend
    (`console.html`, `server.rs` test — done, 2026-08-22).
12. A tensor is read from the shard the index names, and the files served
    are exactly the catalog's (`shards.rs`, `registry/tests.rs` — done,
    2026-10-17).
13. No image reference is parsed before its bytes are shown in the pinned
    transparency log, and a build that pins no log refuses every reference
    (`reference.rs`, `transparency.rs`, `tests/cloud_source_sweep.rs` —
    done on a TEST log, 2026-10-22; no release log exists).
14. Every security guard above has a mutation killer: a campaign on
    2026-08-21 reported 10/10 mutants killed on gate/nras/seal/binding/
    receipt/freshness paths. Its record is not in this repository. Rows
    added later say "mutation-checked" individually; those records are
    not in this repository either.
15. The SDK holds each log checkpoint to the one it remembers: a fork, a
    rollback, or a growth without a consistency proof is refused with the
    relay's 100 (`transparency::remember`, `x0ne-sdk/tests/tlog_consistency.rs`
    — done on the TEST log, 2026-10-31; the memory is the caller's to keep,
    and no public log exists).
